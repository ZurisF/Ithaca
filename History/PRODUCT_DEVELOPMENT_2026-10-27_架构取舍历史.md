# Project Interview Lab：架构取舍历史

> 整理日期：2026-10-27  
> 来源：本轮产品机制澄清对话  
> 用途：记录方案为何从早期的结构化快照、追问链图和集中式报告，收敛为当前讨论的 Markdown、线性 Stage 与分层赛后分析方案。本文记录决策脉络和未决边界，不替代产品开发文档。

## 取舍摘要

| 领域 | 选择 | 放弃或避免的方案 | 取舍原因 |
| --- | --- | --- | --- |
| 项目快照 | 单份用户可读的 `snapshot.md` | Claim/Evidence 数据图、持久化实体 ID、哈希版本和增量缓存 | 快照同时给用户、LLM 和范围解析器使用；可手动保存、导入，减少系统缓存状态。 |
| 面试计划 | 有序 Stage 列表 | 链族、条件分支图、显式目标 Stage 跳转 | 计划规定要覆盖什么，Supervisor 在当前 Stage 内自适应追问。 |
| 实时决策 | 强 Supervisor 语义判断，程序执行有限状态转移 | 用信息增益分数、连续无进展计数器机械裁决 | 判断回答是否足够交给 Supervisor；程序负责动作白名单和线性推进。 |
| Topic | Stage 与题库提供正式 Topic，Supervisor 可创建会话级临时 Topic | 要求 Supervisor 只能从全量 Topic 白名单选择 | 保留临场追问能力；用 RAG 硬过滤和 Prompt 屏蔽约束主题。 |
| 会话上下文 | 完整快照、当前 Stage、动作菜单、1～3 条 RAG 候选和对话 | 将历轮 Supervisor JSON 或多套额外摘要状态回灌 | 内部动作应用到计划状态即可；持续增长的对话每 20 个真实 Q/A 累计 compact。 |
| 赛后分析 | 项目版整场答案、理想版按题处理、并发逐题评估、整场报告 | 一个 Agent 同时读完所有参考答案并包办所有输出 | 以独立逐题评估隔离长上下文，报告 Agent 专注跨题汇总。 |

## 决策记录

### 1. 快照从内部事实图转为 Markdown 文件

早期方案考虑了结构化 Claim、Evidence、内部 ID、哈希、来源清单、快照版本和增量更新。讨论后决定，面向用户和 LLM 的项目上下文直接采用 Markdown；不为 MVP 建立另一套事实图或长期项目缓存。

- 入口为分析用户选择的项目目录并生成 `snapshot.md`，或导入已有 `snapshot.md` 并可选授权对应目录。
- 用户通过输入框补充内容；非空时只在文末追加 `## 用户意见`。用户可以自行选择保存 Markdown，系统不自动长期缓存。
- 只解析 `## Modules` 和 `## Threads` 区域下的 `###` 标题；正文和更深层标题自由，各区域内标题不得重复。
- Planner 接收完整 Markdown 和用户选择的 Module/Thread。快照与后来变化的目录不自动校验；冲突时以快照描述为准。
- Observer 仍需区分事实、推断和未知，不能把推断写成事实；只是无需将这些内容建模为独立 Claim 实体。

### 2. Planner 产出线性 Stage，而不是条件分支图

`interview_plan` 是按顺序执行的 Stage 列表，每项至少包含 `id`、`title`、`goal`、`complete_when` 和 `topic_path`。不在计划中定义链族、条件分支或目标 Stage 跳转；回答带出的细节由 Supervisor 留在当前 Stage 内追问。

Supervisor 每轮从允许动作中选择 `continue`、`complete`、`unresolved` 或 `waived`，并提出一个主要问题。程序据此更新当前 Stage。Supervisor 负责对回答作语义判断，不增加 `coverage`、`information_gain` 等独立评分字段，也不以固定无进展计数器替代判断。自由文本中推断出的跳过意图须经 HITL 确认；跳过按钮点击本身授权。

### 3. 上下文与特殊交互保持轻量

Supervisor 的常规输入约定为：系统 Prompt、完整 `snapshot.md`、当前 Stage、动作菜单、1～3 条 RAG 候选和历史对话。不传难度/Level、原始范围选择或历轮 Supervisor JSON；动作结果反映在计划状态中。完整原始对话另行保留，compact 只用于面试上下文。

- 每满 20 个真实 Q/A，将旧 compact 与新 20 轮原始对话压成一个新的累计 compact；控制按钮、HITL 和刷新不计入真实问答上限。
- Skip 和“不再讨论”按钮会生成默认用户回复补入对话，以保持上下文连贯；这些控制消息不算用户真实作答。
- “换个问法”是刷新当前问题：保持计划、RAG 和正式上下文不变，旧问题及刷新指令不进入对话历史。
- HITL 是对自由文本触发的跳过、Topic 屏蔽和快照追加等状态变更进行鉴权。按钮操作已授权，不重复弹窗；HITL 弹窗和确认不进入对话。
- 快照冲突确认后，用户可编辑 `proposed_user_opinion`；确认后追加至 `## 用户意见`，不覆盖既有内容。

### 4. Topic 兼顾计划导航和临场扩展

Planner 读取完整正式 Topic 列表，并为 Stage 指定 `topic_path`；Supervisor 只看到当前 Stage、RAG 候选和已屏蔽 Topic，不读取完整树。最终问题携带 Topic：可沿用 Stage 或 RAG 的 Topic，也可由 Supervisor 创建会话级临时 Topic。临时 Topic 只进入赛后候选整理，不自动发布到正式主题树或题库。

屏蔽状态保存在 `interview_plan.suppressed_topics`，组装上下文时动态呈现在当前 Stage；RAG 对屏蔽项硬过滤，Prompt 要求 Supervisor 避开，程序不增加语义校验器。UI 显示当前 Topic 和屏蔽列表，用户可以撤销屏蔽。

对话还给出了当前 Stage 的已知处理方式：若当前 Stage 本身正好是被屏蔽的最小粒度 Topic，则标为 `waived_by_user` 并推进；若 Stage 更宽，则保持 active，继续讨论其中未屏蔽内容。受影响的后续 Stage 如何自动处理及记录尚未定案；屏蔽的精确/层级匹配边界也需要在落地前确认。

### 5. 面试结束由计划耗尽或用户操作决定

取消 `propose_complete`、结束确认 HITL、预计问题数量、固定面试长度和最少问题数。所有 Stage 进入终态（`complete`、`unresolved` 或 `waived`）后自动进入赛后流程。保留 100 个真实 Q/A 的内部安全上限；刷新和控制操作不计入上限。`completed_stage_count` 从 Stage 结果即时计算，不单独持久化。

结束规则的对话记录为：正常走完全部 Stage 始终生成报告；强制结束永不生成报告；手动提前结束在 `completed Stage 数量 > 1` 时生成报告，否则不生成。100 轮安全停止按完成 Stage 数量判断。安全停止是否明确沿用 `> 1` 门槛，需确认；后续产品文档曾写为 `>= 1`，与手动结束的对话记录不同。

### 6. 赛后答案、逐题评估和整场报告分层

- **项目版答案 Agent**整场读取最终快照和完整对话，汇总证据缺口；若用户授权了项目目录，可定向取证。只有快照时基于快照回答并标记证据不足。无论目录与快照是否一致，都以快照为基线。Agent 输出所有项目版答案，并产生只增的核验内容；核验章节名称在对话中出现过 `## 赛后项目核验` 与 `## 事后核验` 两种写法，尚未统一。
- **理想版答案**：`adopted` 的正式原题读取预生成理想答案；`rewritten` 和 `generated` 按实际问题现场生成。预生成答案不进入 RAG 或 Supervisor 上下文；现场答案按题隔离，可以并发和单题重试。
- **逐题评估 Agent**：每题独立并发，输入最终快照、本题 Q/A 和两版答案，输出 `comment`，包括反馈、差距、改进建议和证据不足标记；可单题重试。
- **报告 Agent**整场调用一次，只接收最终快照和按顺序排列的 `stage/topic/Q/A/comment`，不接收两版答案，也不重新读取项目目录。输出总评、八维能力观察、项目建议和下一轮训练建议；证据不足时明确标出。
- 用户界面分为“复盘报告”和“完整问答”。对话还讨论了分别由程序组装 `报告.md` 与 `问答.md` 并导出；是否作为最终文件交付要求，应在产品文档中明示。

## 尚未完全定案

1. **报告分数**：讨论中出现“不给评分，没有意义”，但后续答复按不输出数值评分理解，未见明确澄清。需要决定是否提供数值分数，以及是总分还是维度分。
2. **报告门槛**：手动结束的对话记录为 `completed_stage_count > 1`，现有产品文档若采用 `>= 1` 需确认是否有意变更；安全停止的具体阈值也应写明。
3. **Topic 屏蔽传播**：确认精确匹配或层级匹配，并定义哪些后续 Stage 自动豁免、结果如何记录。
4. **Stage 转移与问题归属**：明确 Supervisor 选择 `complete/unresolved` 后，本次输出的问题属于当前 Stage 还是下一 Stage，以及下一 Stage 信息何时进入上下文。
5. **赛后文件与核验标题**：确认是否正式提供可导出的 `问答.md`、`报告.md`，并统一追加到快照的核验章节名。
6. **持久化和失败恢复**：对话确认采用 LangGraph；初步讨论了 Checkpointer 保存运行状态、PostgreSQL 保存业务产物，但两者的状态边界、模型调用失败后的恢复、幂等与并发指令仍未讨论完。此轮不构成最终数据持久化决策。
