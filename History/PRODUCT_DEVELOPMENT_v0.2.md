# 项目模拟面试 Bot：产品开发文档

> 文档状态：Draft v0.2  
> 产品代号：Project Interview Lab（暂定）  
> 首版定位：面向 AI 软件开发岗位项目作者的中文、文本式、证据驱动模拟面试

## 1. 产品摘要

Project Interview Lab 面向 AI 软件开发岗位，读取用户授权的项目材料，生成以 Module 和 Thread 为主体、可复用且带证据的基础项目快照。用户选择面试方向与范围后，系统定向补充所需证据并实例化结构化追问链计划；Supervisor 每轮从计划允许的动作菜单中选择下一步，再结合题库 RAG 和用户回答组织一个问题。面试结束后，彼此隔离的项目版答案 Agent 和理想版答案 Agent 生成两类参考答案，再由报告 Agent 汇总逐题反馈、候选人画像、项目改进建议和下一轮训练建议。

它解决的不是“多刷几道八股题”，而是三个更具体的问题：

1. 项目作者知道自己做过什么，却未必能清楚说明为什么这样做。
2. 通用面经无法根据具体项目持续追问，训练容易停留在背诵。
3. 面试结束后缺少基于原回答证据的复盘，用户不知道下一次该改哪一句。

## 2. 产品目标与非目标

### 2.1 目标

- 将代码、文档和用户补充信息整理为可追溯、可缓存的 Module/Thread 项目快照。
- 生成与项目特征、AI 软件开发岗位能力和用户水平匹配的问题。
- 根据面试方向与范围生成结构化计划，用可维护的追问链族控制节奏，同时保留问题表达和追问的适应性。
- 将实时面试与赛后答案、评估隔离，在保持面试连贯性的同时降低每轮延迟和成本。
- 输出细粒度、可验证、可执行的复盘报告，并将散落在面试过程中的工程缺口汇总为项目改进建议。
- 将高价值新问题沉淀为候选题，经查重和质量门禁后进入题库。

### 2.2 非目标

- 不在 MVP 中替企业作招聘、淘汰或录用决定。
- 不把用户归类为固定人格或生成带歧视风险的“人才标签”。
- 不承诺从代码中准确还原所有业务背景、规模数据和个人贡献。
- 不自动替用户润色或伪造不存在的项目经历。
- 不在 MVP 中覆盖语音、视频、表情和肢体表现分析。
- 不覆盖与 AI 软件开发无关的通用前端、后端、算法或工程效率岗位面试。
- 不把产品做成通用代码审查、IDE 或在线判题平台。
- 不让系统生成的新问题未经审核直接进入正式题库。

## 3. 用户与使用场景

### 3.1 核心用户

- 准备实习、校招或社招 AI 软件开发岗位面试的项目作者。
- 希望重新梳理 AI 项目、补齐表达和技术理解的开发者。
- 带教者或课程教师，用同一项目反复组织结构化模拟面试。

### 3.2 核心场景

1. **首次梳理**：用户导入项目，发现自己没有准备过的架构、边界和评估问题。
2. **定向训练**：用户选择面试方向和一个或多个 Module、Thread 或横切主题，完成对应追问链。
3. **项目改进**：将面试中暴露的问题与行业理想实践汇总，形成符合现有项目边界的改进清单。
4. **复盘重练**：系统依据上轮薄弱项组织下一轮面试，并对比前后回答。

## 4. 核心设计原则

### 4.1 证据优先

任何项目结论必须属于以下三类之一：

- **事实**：可由代码、文档、配置或用户陈述直接支持。
- **推断**：由事实推导而来，必须记录证据、推断理由和置信度。
- **未知**：当前材料无法回答、但面试中值得询问的内容。

系统不得把推断悄悄改写成事实。用户补充的信息同样要标明来源为“用户陈述”。

### 4.2 实时面试与赛后分析隔离

Supervisor 只能访问当前面试视图、结构化计划与动作菜单、题库检索结果、会话状态和公开对话。它不读取项目版或理想版答案，不在面试热路径中重新检查代码，也不负责对用户进行详细评分。用户回答在面试中先作为“用户陈述”记录；事实核验、参考答案和候选人画像在正常完成面试后生成。

项目版答案 Agent 与理想版答案 Agent 使用独立上下文。报告 Agent 只接收它们已经完成的结构化产物和面试记录，不参与两类答案的生成，避免相互暗示。

### 4.3 追问胜过题量

问题编排由版本化的追问链族控制，而不是只依靠 Supervisor 临场决定或不断切换主题。链族描述阶段目标、适用条件、可选分支和完成条件，不写死具体问题。一个常见链条可以是：

`事实确认 → 设计动机 → 备选方案 → 约束变化 → 故障或边界 → 个人贡献 → 复盘改进`

面试计划决定“还需要完成什么”，Supervisor 决定“结合此刻回答具体怎么问”。

### 4.4 反馈必须可执行

不输出“架构能力较强”一类空泛结论。每个判断使用统一结构：

`回答证据 → 能力信号 → 缺失或风险 → 置信度 → 下一步练习`

### 4.5 项目建议必须经过汇总

面试中的理想答案只解决单题参照问题。面试结束后，报告 Agent 必须结合项目边界、项目实际情况、完整面试对话和各题行业理想版答案，生成综合报告，并在其中去重、归类形成项目级改进建议。只整理根据现有项目可以判断的改进点，不把脱离项目实际的行业最佳实践机械地列为待办。

### 4.6 题库迭代必须受控

系统可以自动积累实际提问、用户反馈并整理候选题，但不能自动改写正式题库。新问题只有通过隐私处理、语义查重、适用性检查和人工确认后，才能进入正式题库。追问链族、Prompt、行为 Schema、主题树和监督规则属于普通的软件配置演进：记录失败案例、加入回归测试、审核通过后发布，不把它们包装成在线“自更新”。所有变更保留版本、审核记录和撤回能力。

## 5. 完整用户流程

### 5.1 创建项目

用户：

1. 创建项目并选择材料来源。
2. 授权本地目录、Git 仓库或上传文档。
3. 补充项目目标、明确边界和代码中无法直接确认的背景；目标岗位固定为 AI 软件开发。
4. 确认系统可读取的文件范围与排除规则。

系统：

1. 建立文件清单，过滤二进制、依赖目录、敏感文件和超大文件，并在解析前替换疑似密钥。
2. 解析脱敏后的代码、配置和文档，生成 Project Header、Module、Thread、证据索引和文件哈希。
3. 展示事实、推断、未知项和引用位置，请用户纠错或补充。
4. 将确认后的基础快照、脱敏切片、证据索引和来源哈希保存为可版本化、可增量复用的项目上下文快照。

### 5.2 发起模拟面试

用户选择：

- AI 软件开发岗位的面试级别与难度。
- 面试方向：项目导览、核心链路深挖、横切专项、压力面试、贡献与复盘。
- 面试范围：全项目、指定 Module、指定一条或多条 Thread，或横切专项的具体主题。

系统先从基础快照生成当前会话的定向项目视图，再选择并实例化追问链族，形成结构化面试计划。界面只展示方向、范围和预计问题数量，不提前展示完整问题清单；预计数量用于说明节奏，不是截断上限。

### 5.3 面试进行中

每一轮：

1. 编排器根据当前追问链阶段、已完成项、条件分支和用户屏蔽内容生成允许的计划动作菜单。
2. 题库 RAG Hook 根据当前面试视图、链与阶段、最近回答和已问内容召回 3～5 条候选问题。
3. Supervisor 在同一次调用中识别上一条用户消息（首轮除外），从动作菜单选择一个 `plan_action_id`，并只提出一个主要问题；它不检查代码，也不判断回答是否符合项目事实。
4. 编排器校验并应用合法的计划动作，再向用户展示问题。
5. 用户回答，或声明“不知道”“跳过”“问题不成立”；下一轮 Supervisor 据此决定继续当前阶段、推进、进入条件分支或记录未决，但不能绕过计划约束。

用户可以暂停、主动完成、强制退出、收藏问题或给问题差评。收藏与差评不打断回答流程；“切换主题或跳过当前阶段”是单独的会话控制，不等同于对题目质量的评价。暂停后可从状态快照恢复。

#### 面试完成与退出

- **主动完成**：用户认为本场面试已经足够时，可以主动完成。系统保存已提交的回答，并按常规赛后流程生成综合报告。
- **强制退出**：立即终止面试，不再进行后续回答分析，也不生成综合报告。该操作必须二次确认，避免误触。
- 系统默认以追问链完成为结束条件，不让固定题数截断尚未完成的链。
- 所有必需链阶段已经完成，或因不适用、用户屏蔽等原因被明确跳过后，Supervisor 才可以提议完成；用户可以确认完成或选择继续。
- 系统保留 100 轮的内部安全上限，只用于阻止异常循环，不作为用户可见的面试长度。触发时按 `safety_cap` 记录原因并进入正常收尾。

### 5.4 面试复盘

面试正常完成后，项目版答案 Agent 与理想版答案 Agent 并行生成两类参考答案；报告 Agent 再结合项目边界、项目实际情况、面试对话和两类答案生成一份综合报告，包含：

- 完整问答历史和时间线。
- 每道题的考察意图、逐条反馈和回答改写建议。
- 基于项目证据的参考答案。
- 在理想工程条件下的参考答案。
- 能力表现图谱及其证据和置信度。
- 项目事实新增信息、矛盾项和待补材料。
- 去重整理后的项目改进建议。
- 下一轮推荐训练主题与建议题目。

## 6. 功能需求

### 6.1 项目材料接入

#### MVP

- 读取用户指定的本地项目目录。
- 支持常见代码、Markdown、纯文本、JSON、YAML 和 TOML。
- 支持 `.gitignore`，并提供额外排除规则。
- 展示读取文件清单、跳过原因和解析错误。
- 默认跳过 `.env`、私钥、凭据文件和凭据目录。
- 使用轻量规则扫描器检测 API Key、Token、密码、私钥和带密码的连接串；可采用 `detect-secrets` 加少量自定义规则。
- 命中的值在切块前替换为带类型的占位符。只有脱敏文本可以进入索引、模型上下文和日志；本地原文件保持不变。
- 界面展示命中文件、行号和类型，不回显敏感值。MVP 不对姓名、邮箱等一般个人信息做大范围自动替换，避免误伤正常代码。

#### 后续

- GitHub/GitLab 授权接入。
- Issue、PR、提交记录和设计文档接入。
- 多项目关联与项目版本差异分析。

### 6.2 基础项目快照与面试视图

系统不为首次导入生成一份试图覆盖所有角度的巨大画像，而是建立一个可复用的基础项目快照：

- **Project Header**：项目目标、用户、明确边界和主要技术栈，只保留理解项目所需的薄层信息。
- **Module**：相对稳定的结构单元，记录职责、接口、依赖、主要数据和证据引用，回答“项目有什么”。
- **Thread**：端到端业务或运行链路，记录触发点、经过的 Module、状态或数据变化、外部调用、失败路径和证据引用，回答“项目怎么跑”。

测试、安全、性能、评估和可观测性等横切信息附着在相关 Module、Thread 和证据上，不在基础快照中预先扩张成大量独立栏目。个人贡献无法仅凭代码可靠判断，默认作为待面试确认的未知项。

基础快照中的判断仍以 Claim 保存，并区分 `fact | inference | unknown | disputed`；事实与推断必须指向脱敏后的文件、配置、文档或用户陈述。未在已扫描范围内发现某项实现，只能记为未知或“未发现证据”，不能直接断言它不存在。

项目上下文快照还包含授权文件清单、跳过原因、来源哈希、脱敏切片和证据索引。它按文件哈希缓存，项目变化时只更新受影响的 Module、Thread 和证据，不重新分析整个项目。

每场面试再根据“方向 × 范围”从基础快照生成 `interview_view`：项目导览使用全局粗粒度信息；核心链路深挖补读选定 Thread 及相关实现；横切专项聚合范围内的对应证据；压力面试补充约束、故障和替代方案；贡献与复盘重点整理决策点和未知项。面试视图可按基础快照版本、方向、范围和配置版本缓存复用。

赛后 Agent 遇到证据不足时可以发起结构化 `evidence_request`，局部读取相关文件和邻近代码。Supervisor 只能访问已经生成的面试视图，不具备读取源文件的能力。

项目事实采用“不可变基线 + 追加式修正”的方式维护：

- 初次分析并经用户审阅的基础快照是有证据的基线，不在面试中原地覆盖或删除。
- 只有用户陈述与当前视图发生明显、直接冲突时，Supervisor 才标记 `possible_project_conflict`；它不读取代码，也不主动寻找细微矛盾。
- 界面向用户展示基线 Claim、冲突陈述及对应消息。用户确认后，系统追加一个会话级 `project_overlay`，从下一轮起进入有效项目视图。
- Overlay 在语义上可以补充或声明替代某条 Claim，但存储上只追加新记录，并保留替代关系和全部历史。
- 用户确认只代表“本场面试暂按此说法继续”。赛后项目版答案 Agent 结合证据将其标记为已验证、未支持或仍待核实；永久更新基线需要证据复查或快照审阅。

### 6.3 面试方向、范围与追问链计划

首版提供五种面试方向：

| 面试方向 | 计划目标 | 面试视图侧重 |
| --- | --- | --- |
| 项目导览 | 覆盖关键 Module 和 Thread，建立完整项目叙事 | 全项目粗扫、入口、主要结构与关键链路 |
| 核心链路深挖 | 集中训练一至两条端到端链路 | 选定 Thread、相关 Module、数据与细节实现 |
| 横切专项 | 检查测试、安全、性能、评估或可观测性 | 在所选范围内聚合对应证据和边界 |
| 压力面试 | 通过约束变化、故障、反例和替代方案检验理解 | 容量假设、失败路径、降级和技术取舍 |
| 贡献与复盘 | 澄清个人职责、技术判断、失败与改进 | 决策点、用户陈述、未知项和项目结果 |

面试范围可以是全项目、一个或多个 Module、一个或多个 Thread，或横切专项中的具体主题。方向决定“如何问”，范围决定“问哪里”。

追问链族是与 Prompt 同级的版本化配置。每个链族至少描述：

- 适用的面试方向和范围类型。
- 一组具有目标和完成条件的阶段。
- 必需阶段、条件分支和允许跳过的情况。
- 阶段之间允许的转移，以及完成整条链的条件。

链族不保存固定问题。面试规划 Agent 根据当前视图选择链族并实例化为 `interview_plan`；链负责控制方向和进度，Supervisor 负责结合当前回答组织具体问题。计划为每轮生成有限的 `allowed_plan_actions`，例如继续当前失败路径、推进到验证阶段、开启一个满足条件的分支或完成当前链。

计划中的所有必需阶段完成或被明确跳过后，编排器才允许 Supervisor 输出 `propose_complete`。用户主动完成仍可随时进入正常赛后流程；100 轮只作为不可配置的异常循环安全上限。

### 6.4 面经题库与检索

本产品不是基于 NLP 意图识别和固定回复的 FAQ 系统。面试由 Supervisor 主导，题库 RAG 只是每轮自动执行的检索 Hook，为下一步决策提供有限参考，不直接决定 Supervisor 必须问什么。

题目对象包含：

- 题目正文与标准化语义。
- 考察能力和适用项目特征。
- AI 软件开发级别、难度和预计用时。
- 一个主要的层级化 `topic_path`，以及可选的辅助标签。
- 适用的追问链阶段，以及首问、澄清问题和可选追问变体。
- 版本、审核状态和必要的版权或授权状态。
- 题目向量和关键词。

题库不以作者身份或“是否由 AI 提出”作为质量字段。运行时只记录当前问题与已有题库的派生关系，用来防止重复入库，而不是追溯英雄出处。

题库不保存标准答案。项目版和理想版答案在面试正常完成后根据实际问题生成。

检索采用混合策略：

1. 每轮提问前自动调用检索 Hook，根据当前面试视图、追问链与阶段、允许的计划动作、最近回答、已问内容和会话状态构造查询。
2. 使用向量检索召回语义相关题。
3. 使用关键词检索补回具体技术名和错误码等精确命中。
4. 按难度、主题和审核状态过滤；最近 3 轮已经使用过的题目进入冷却期，不得再次进入候选集。
5. MVP 使用 RRF 合并向量与关键词排名，再用确定性规则考虑当前链阶段、重复度和追问连续性；不增加逐轮重排模型调用。
6. 每轮向 Supervisor 返回 3～5 条候选；不足 3 条合格结果时不强行补足。
7. Supervisor 可以采用、改写或忽略候选题，不直接把 Top 1 当最终问题，也不照题库返回固定回复。

MVP 默认使用 RRF 合并向量与关键词排名；后续再引入专用重排模型。

### 6.5 Supervisor Agent

Supervisor 是实时面试中唯一的对话模型调用。它在每轮接收当前面试视图、结构化计划、允许的计划动作菜单、公开对话、会话状态和 RAG 候选，完成以下工作：

- 识别一条用户消息中并存的回答、提问、跳过、纠错、切换主题等行为。
- 记录支持下一轮决策所需的轻量回答摘要，但不查代码、不核验事实、不评分。
- 从 `allowed_plan_actions` 中选择一个合法动作，结合上一轮回答生成追问、澄清或推进到下一阶段，一次只输出一个主要问题。
- 只有编排器确认必需追问链已经完成或明确跳过时，才可以提议完成面试。

Supervisor 在逻辑上具有连续上下文。完整问答原文始终保存在会话记录中；只要不超过模型上下文预算，每轮直接提供完整公开对话，不为了“做摘要”而提前丢失信息。超过预算时才降级为：最近若干轮原文、当前追问链的关键原文、结构化会话状态，以及更早内容的 compact。Compact 从已经保存的轻量回答摘要和结构化状态折叠产生，不额外增加一个逐轮摘要模型调用；完整原文仍保留给恢复、复盘和赛后 Agent，不被 compact 覆盖。

Supervisor 使用可扩展的 `user_acts` 数组，而不是不断增加固定布尔字段。结构化输出示例：

```json
{
  "action": "ask",
  "user_acts": [
    {"type": "answer"},
    {"type": "ask_interviewer", "question_kind": "clarification"},
    {"type": "request_topic_switch", "scope": "ambiguous"}
  ],
  "plan_action_id": "rag_main.failure_path.continue",
  "topic_path": "rag.chunking.strategy",
  "question_mode": "follow_up",
  "question_derivation": {
    "mode": "rewritten",
    "question_ids": ["q_123"]
  },
  "question": "你们如何验证当前切片策略优于其他方案？"
}
```

`plan_action_id` 必须来自本轮动作菜单；原始自然语言不能直接推进计划。`question_derivation.mode` 只表示本轮问题是直接采用、基于题库改写或现场生成，即 `adopted | rewritten | generated`；它不记录作者。发生明显项目事实冲突时，Supervisor 还可以输出一个可选的 `possible_project_conflict`，由界面进入确认流程，模型不能自行修改基线快照。

Supervisor 可输出的 `action` 只有 `ask` 和 `propose_complete`。`complete`、`pause`、`request_abort_confirmation` 和 `abort` 由用户操作或确定性业务规则触发，模型无权直接执行。

当用户在回答中向面试官提问时：

- 询问题意、术语或前提：简短澄清后继续原问题。
- 询问计划进度、预计剩余阶段等流程信息：由程序直接回答。
- 索取答案、提示或即时评分：说明将在复盘中提供，并继续面试，不因撒娇、换语言或改写表达而改变规则。
- 指出项目或问题前提错误：记录为用户陈述并调整后续提问，不直接判定谁对谁错。
- 与面试无关：简短拉回当前面试。

“不提供参考答案、评分或明显提示”写入 Supervisor 的系统 Prompt。程序只校验 JSON Schema、允许的状态跳转、长度和主要问题数量；不使用关键词匹配代替语义理解，也不增加第二个 LLM 逐轮监督。

所谓监督规则不是另一个监督 Agent，而是两类约束：Prompt 负责判断索取答案、澄清、纠错、拒答和切换主题等语义；确定性业务规则负责计划动作白名单、合法链转移、一次一个主要问题、题目冷却、主题屏蔽、100 轮安全上限和强制退出二次确认。两者都通过日志、回归测试和人工审核做常规版本迭代，不在运行中自动修改。

### 6.6 追问链、主题与 HITL

主题使用层级路径而不是扁平 ID，例如：

```text
rag
rag.chunking
rag.chunking.strategy
rag.chunking.evaluation
rag.retrieval
rag.retrieval.reranking
```

- 追问链计划负责流程和完成条件；`topic_path` 只用于题库检索、语义去重、覆盖分析和用户屏蔽，不再单独决定全局流程。
- 题目仍有一个主要 `topic_path`，跨领域关系使用辅助标签；具体问题继续使用三轮 RAG 冷却和语义去重。
- 当某阶段已经达到完成条件，编排器不再提供无意义的继续追问动作；若连续回答没有带来新信息，应推进阶段、记录为未决或提供允许的替代分支，而不是原地钻牛角尖。
- 用户明确说“别问切片”时屏蔽 `rag.chunking`；明确说“别聊 RAG”时屏蔽整个 `rag`。
- 用户只说“换个方向”等范围不明确的话时，Supervisor 返回 HITL 请求，由界面根据当前计划提供“跳过当前阶段”“跳过当前链中的该主题”或“在整场面试中屏蔽该主题”等选项。该确认不计为一个问答轮次。
- 已屏蔽主题以标签显示在界面上，用户可随时取消；屏蔽或取消从下一轮生效，只影响当前面试。
- 被用户明确跳过或屏蔽的必需阶段以 `waived_by_user` 记录，视为已处理但不伪装成已回答；RAG Hook、动作菜单和 Supervisor 都必须过滤当前会话的 `suppressed_topic_paths`。

### 6.7 赛后答案 Agent

面试正常完成后，并行运行两个上下文隔离的 Agent：

1. **项目版答案 Agent**：读取当前问题、相关对话和项目上下文快照，必要时通过 `evidence_request` 局部检查代码，核验用户陈述并生成基于项目证据的参考答案。缺少证据的内容必须明确说明。
2. **理想版答案 Agent**：只读取当前问题、面试级别和必要的一般背景，不读取项目材料、项目版答案或候选人评价，生成行业理想条件下的参考答案。

两类 Agent 输出答案要点、允许的合理变体和必要引用。实时面试阶段不生成参考答案，以降低延迟、成本和泄漏风险。

### 6.8 复盘报告

报告分为四层：

1. **会话层**：完整历史、题目路径、用时、跳过和中断。
2. **逐题层**：回答摘要、做得好的部分、缺失、矛盾、参考答案和改写示例。
3. **能力层**：基于本场回答形成候选人画像，包括需求理解、系统设计、技术深度、工程质量、故障思维、数据意识、沟通结构和复盘能力。
4. **项目层**：项目事实更新、未决问题、项目可改进项和建议补充的证据材料。

能力层只呈现与本次会话相关的观察，不声称是对人的永久评价。

综合报告由报告 Agent 在面试结束后统一生成，输入包括：

1. 用户确认的项目目标、范围、约束和明确的非目标，即项目边界。
2. 代码、文档、基础快照和当前面试视图所反映的项目实际情况。
3. 完整面试对话中暴露的缺口、矛盾、未知项和用户补充事实。
4. 各题的项目版与理想版参考答案，以及项目版答案 Agent 已完成的事实核验结果。

报告 Agent 默认不重新阅读整个项目。只有当现有产物不足以支撑一条重要项目建议时，才可以发起局部 `evidence_request`。每条建议包含建议内容和来源，系统应合并跨题重复建议。项目改进建议是面试复盘的整理结果，不等同于完整代码审查。

### 6.9 题库迭代与对话配置演进

Supervisor 实际问出的问题是题库迭代的主要材料。完整问题本来就属于面试记录，因此不再建立一套沉重的“每题分析档案”，只给每轮附加最小元数据：关联的题库 ID、`adopted | rewritten | generated` 派生关系，以及用户反馈。

面试界面在每道问题旁提供两个轻量入口：

- **收藏**：表示这道题有价值。正式题库中的原题只增加正向信号；被改写或现场生成的问题优先进入候选题整理队列。
- **差评**：表示这道题在当前语境下存在问题，可选“重复、不相关、表述不清、其他”原因。单次差评不自动删除或降权，多次出现同类问题时才进入维护队列。

“不想继续这个主题”仍走主题切换或屏蔽流程，不能当成题目差评。系统也不根据低使用频率自动清理题目：冷门、小众问题可能只适用于少数项目，低频不等于低质量，过时与否也不能仅由热度判断。

正常完成面试后，离线题库整理 Agent 可以批量处理被改写、现场生成、收藏或反复差评的问题，不进入实时面试热路径：

1. 删除或泛化私有项目名、业务数据、人员和实现细节。
2. 将问题改写为脱离原项目仍可复用的表达；无法安全泛化的内容只保留在私有会话中。
3. 与正式题库和候选池进行精确、语义查重。
4. 与已有题高度相似时整理为变体或追问分支，否则生成新候选题。
5. 补充适用项目特征、难度、`topic_path` 和必要的追问关系。
6. 经过人工审核后发布为新的题库版本；整理 Agent 无权自动入库。

候选题可以保留受权限保护的原始会话引用，正式题库不得包含用户私有项目细节。题库整理可以使用成本较低的模型或批处理任务，不增加每轮面试延迟。

追问链族、Supervisor Prompt、`user_acts` Schema、主题树和监督规则统一视为“对话配置”。系统收集误判、越权输出、重复追问和用户纠错案例，形成修改建议和回归样本；修改后通过测试与人工审核再发布。行为 Schema 不自动扩张，也不为了制造“自迭代”概念而增加额外机制。

### 7.2 状态机

MVP 使用 LangGraph 实现下列显式状态机。用户回答和 HITL 选择通过 interrupt 暂停与恢复；每轮先生成允许的计划动作菜单，再由题库 RAG Hook 召回候选并进行一次 Supervisor 调用。项目版与理想版答案只在面试正常完成后并行生成。LangGraph 负责编排，业务状态和产物仍以 PostgreSQL 中的数据为准。

```text
PROJECT_INGESTING
  → BASE_PROJECT_SNAPSHOT
  → SNAPSHOT_REVIEW
  → READY
  → INTERVIEW_VIEW_BUILDING
  → INTERVIEW_PLANNING
  → PLAN_ACTION_MENU
  → QUESTION_RAG_HOOK
  → SUPERVISOR_DECISION
  → ASKING
  → USER_INPUT_RECEIVED
  → PLAN_ACTION_MENU
  → QUESTION_RAG_HOOK
  → SUPERVISOR_DECISION
      ├─ ask(valid plan_action_id) → APPLY_PLAN_TRANSITION → ASKING
      ├─ ask + possible_project_conflict → HITL_PROJECT_OVERLAY → APPLY_PLAN_TRANSITION → ASKING
      ├─ user_act.topic_switch(scope=ambiguous) → HITL_TOPIC_SCOPE → PLAN_ACTION_MENU
      └─ propose_complete(required_chains_resolved) → COMPLETE_CONFIRMATION
          ├─ continue → ASKING
          └─ complete → FINALIZING

FINALIZING
  → PARALLEL_REFERENCE_ANSWERS
      ├─ project_grounded_answer
      └─ ideal_answer
  → REPORT_GENERATION
  → REPORT_READY

ASKING / PAUSED
  ├─ user_complete → FINALIZING
  └─ user_force_exit → EXIT_CONFIRMATION
      ├─ cancel → previous_state
      └─ confirm → ABORTED

ASKING
  └─ user_pause → PAUSED → user_resume → PLAN_ACTION_MENU

ANY_ACTIVE_INTERVIEW
  └─ hard_cap(100) → FINALIZING(termination_reason=safety_cap)
```

正常完成会话后可以异步触发题库整理，不阻塞报告生成；强制退出的会话不触发赛后分析或题库整理。

### 7.3 上下文复用与隔离

- 基础项目快照是所有后续组件共享的持久化事实层；复用的是 Project Header、Module、Thread、脱敏切片、证据索引和来源哈希，而不是某次模型调用的原始上下文。
- 每场面试基于“基础快照版本 + 方向 + 范围 + 配置版本”生成并缓存定向面试视图。会话级 Overlay 与证据基线分开保存，叠加后构成 Supervisor 当前可见的有效视图。
- 完整面试原文是不可丢失的会话记录。MVP 在上下文预算允许时向 Supervisor 提供全部公开对话；超过预算时使用“最近原文 + 当前追问链关键原文 + 结构化状态 + 早期 compact”的滑动窗口。当前问题与用户最新回答必须保留原文。
- Supervisor 上下文：有效面试视图、结构化计划、本轮动作菜单、题库候选、上述连续对话上下文、主题屏蔽和链进度。它不能局部读取源文件，也看不到赛后答案和评价。
- 项目版答案上下文：当前问题、必要对话和按需检索的项目证据；不能访问理想版答案。
- 理想版答案上下文：当前问题、面试级别和一般背景；不能访问项目材料、项目版答案和用户评价。
- 报告上下文：面试记录、两版最终答案和事实核验结果；默认不重放整个代码库，必要时才发起局部证据请求。

所有 Agent 输出使用 JSON Schema 校验。原始自然语言输出不得直接驱动数据库写入或状态跳转。

## 8. 技术架构

### 8.1 逻辑架构

```text
Web Client
   │
API / Session Service
   ├── Project Ingestion Pipeline
   │      ├── File inventory & sensitive content filter
   │      ├── Parser / chunker
   │      └── Header / Module / Thread snapshot / evidence index
   ├── Interview View & Planning
   │      ├── direction & scope evidence builder
   │      ├── chain family registry
   │      └── structured plan / allowed action menu
   ├── Interview Orchestrator
   │      ├── Question RAG Hook
   │      ├── Supervisor
   │      └── Chain state / topic suppression / HITL controls
   ├── Post-interview Analysis
   │      ├── Project-grounded Answerer
   │      ├── Ideal Answerer
   │      └── Report Generator
   ├── Offline Question Curation
   │      ├── privacy generalization / dedup
   │      └── candidate & maintenance queue
   ├── Retrieval Service
   │      ├── Question bank
   │      ├── Project evidence index
   │      └── Hybrid search / rerank
   └── Evaluation & Observability
          ├── traces / prompt versions
          ├── offline eval runner
          └── feedback events

PostgreSQL + pgvector   Object Storage   Optional Redis/Queue
```

### 8.2 建议技术选型

以下是首版技术选型；编排层确定使用 LangGraph：

| 层 | 建议 | 原因 |
| --- | --- | --- |
| Web | Next.js + TypeScript | 会话 UI、报告页和服务端渲染可放在一个工程中 |
| API | Python + FastAPI | 适合模型调用、检索和评估生态；类型模型清楚 |
| 编排 | LangGraph + 显式业务状态机 | 支持暂停、恢复、条件分支和并行分析；业务状态仍落 PostgreSQL |
| 敏感信息过滤 | `detect-secrets` + 少量自定义规则 | 用正则、关键词和熵检测覆盖常见凭据，不增加 LLM 调用 |
| 主数据库 | PostgreSQL | 会话、项目快照、面试计划、题库、版本和审计关系清晰 |
| 向量检索 | pgvector | MVP 减少基础设施；数据量或延迟超限后再拆专用向量库 |
| 关键词检索 | PostgreSQL FTS | 与 pgvector 组成低运维成本的混合检索 |
| 对象存储 | S3 兼容存储；本地开发用文件目录 | 保存导入材料、报告和可重建产物 |
| 异步任务 | MVP 使用进程内任务或数据库任务表；规模化后用队列 | 避免过早引入 Redis/Celery 运维成本 |
| 模型接入 | 供应商无关 Adapter | 区分访谈、抽取、向量和评分模型，便于替换与评估 |
| 上下文缓存 | 基础快照 + 面试视图 + 文件哈希 + 证据索引 | 同一项目和相同方向/范围复用结构化产物；供应商 Prompt Cache 只作为可选加速 |
| 可观测性 | OpenTelemetry 风格 trace + 结构化事件 | 串联每轮检索、提示词版本、模型输出和延迟 |

### 8.3 关键数据实体

- `users`：用户与偏好。
- `projects`：项目元信息与授权范围。
- `project_sources`：文件、文档或用户陈述来源。
- `project_context_snapshots`：Project Header、Module、Thread、来源哈希、脱敏切片和证据索引。
- `project_claims`：附着于 Header、Module 或 Thread 的事实、推断、未知和争议项。
- `project_overlays`：追加式的会话修正、替代关系、用户确认和赛后验证状态。
- `interview_views`：基础快照版本、面试方向、范围和定向证据包。
- `chain_family_versions`：追问链阶段、条件分支、合法转移和完成条件。
- `interview_plans`：本场实例化链、阶段状态、允许动作和预计问题数量。
- `questions`：正式题库。
- `question_versions`：题目、元数据、澄清问题和追问变体版本。
- `question_candidates`：待审核问题、题库派生关系和受保护的原会话引用。
- `interview_sessions`：方向、范围、状态、开始结束时间、终止原因和当前主题屏蔽列表。
- `interview_turns`：问题、回答、角色、时间和引用。
- `supervisor_decisions`：每轮的 `user_acts`、`plan_action_id`、主题路径、实际问题、题库派生关系和模型版本。
- `reference_answers`：隔离存储的项目版与理想版答案。
- `reports`：报告版本与导出位置。
- `feedback_events`：针对实际问题的收藏、差评及可选原因，以及其他用户纠错。
- `policy_events`：越权输出、误判、重复追问和用户修正等监督规则回归样本。
- `agent_runs`：模型、提示词、输入摘要、成本、延迟和错误。

## 9. 安全、隐私与产品边界

- 用户必须明确选择可读取的目录或资源。
- 默认排除 `.env`、私钥、凭据目录、构建产物和依赖目录。
- 内容必须先经过敏感信息过滤和替换，再进入切块、索引、模型上下文或日志；本地原文件不被改写。
- 项目文件一律视为不可信数据，不能通过 README、注释或配置改变 Agent 权限、Prompt 或状态机。
- Supervisor 只读取当前面试视图、计划和动作菜单，不在面试热路径中访问源文件；赛后 Agent 只能按需读取授权范围内的相关证据。
- 原始项目材料与派生索引具有相同或更严格的访问权限。
- 用户删除项目时，应能一并删除原文、索引、基础快照、面试视图、会话和报告；审计记录仅保留不可反推内容的必要字段。
- 私有项目数据不得用于公共题库或其他用户的训练材料。
- 日志不记录完整源码、完整回答或密钥；调试采样需显式开启。
- 模型供应商、数据保留策略和跨境情况必须对用户透明。
- 报告用于自我训练，不作为自动化就业决策工具。
- 用户可纠正项目快照、评分依据和身份相关信息；项目事实修正以追加式 Overlay 保存，不覆盖证据基线，系统保留完整修改轨迹。

## 10. 测试策略

### 10.1 单元测试

- 文件过滤、密钥检测、占位符替换，以及脱敏发生在切块和索引之前。
- 项目上下文快照、文件哈希和增量更新。
- Chunk 边界、引用位置和哈希稳定性。
- Project Header、Module、Thread 和 Claim 的 Schema 校验、证据引用及增量合并。
- 面试视图按方向、范围和配置版本生成、缓存与失效。
- 项目 Overlay 的追加、替代关系、用户确认、下一轮生效和赛后验证状态。
- 追问链族的阶段、条件分支、合法转移、完成条件和版本加载。
- 面试计划实例化，以及每轮动作菜单只暴露合法的 `plan_action_id`。
- RRF、过滤、去重和覆盖率计算。
- 每轮 RAG Hook 返回 3～5 条候选，并排除最近 3 轮处于冷却期的题目。
- `user_acts`、Supervisor 动作白名单和单一主要问题的 Schema 校验。
- `question_derivation` 的 adopted、rewritten、generated 三类关系及关联题目 ID 校验。
- 链完成或明确跳过后才允许系统提议结束；100 轮安全上限不可由模型或用户修改。
- 主题屏蔽、链阶段 `waived_by_user` 和下一轮取消屏蔽。
- 面试状态机的合法与非法跳转。
- 暂停、恢复、重试和幂等行为。
- 主动完成会生成综合报告；强制退出必须二次确认，且不会触发后续分析和报告生成。
- 评分与报告聚合的确定性逻辑。
- 项目改进建议的跨题去重和来源保留。

### 10.2 集成测试

- 小型固定仓库从导入到 Module/Thread 基础快照的完整链路。
- 五类面试方向和不同范围能够生成不同的面试视图与追问链计划。
- PostgreSQL FTS 与 pgvector 的混合检索。
- 模型 Adapter 的超时、限流、空输出和格式错误。
- 面试热路径不得调用项目证据服务、参考答案 Agent 或报告 Agent。
- 项目版与理想版答案并行完成顺序不同的竞态测试。
- 项目版与理想版答案的输入上下文相互隔离；两类答案和评价内容不得进入 Supervisor 上下文。
- 报告 Agent 能读取项目边界、面试对话、事实核验和两版参考答案，并保留每条项目建议的来源。
- HITL 主题范围选择不占面试轮数，屏蔽和取消从下一轮生效。
- Supervisor 只能选择本轮动作菜单中的 `plan_action_id`，非法动作不能推进链状态。
- 明显项目事实冲突经用户确认后只生成会话 Overlay，不覆盖基线，并从下一轮进入 Supervisor 的有效视图。
- Supervisor 上下文超过预算后仍保留当前问题、最新回答和当前追问链关键原文；完整原文可用于恢复和赛后分析。
- 题库整理能够去除私有项目细节、合并重复问题，并且只能生成候选题，不能自动发布。
- 删除项目后检查派生数据是否完整清除。

### 10.3 端到端测试

建立 5～10 个不同类型的“黄金项目包”，每个包含：

- 固定代码和文档。
- 人工标注的 Project Header、Module、Thread、项目事实、合理推断和未知项。
- AI 软件开发面试方向、范围、预期链阶段和允许动作。
- 多档用户回答脚本。
- 预期追问行为和报告要点。

覆盖正常完成、链条件分支、阶段跳过、用户纠错、拒答、长回答、矛盾回答、项目材料不足、中途暂停、模型失败、混合“回答 + 提问”、多语言索取答案、模糊主题切换和异常循环安全停止。

### 10.4 Prompt 与模型回归测试

- 每次变更提示词或模型前运行固定样本集。
- 结构化输出成功率必须达到发布门槛。
- 验证用户以不同语言、撒娇、角色指令或间接表达索取答案时，Supervisor 仍不提供答案、提示或即时评分。
- 验证正常回答末尾附带提问时，回答内容和用户提问能够同时被识别。
- 验证每轮只产生一个主要问题，且主题切换请求得到尊重。
- 验证 Supervisor 不选择动作菜单以外的路径，链完成前不自行提议结束。
- 比较问题相关性、重复率、无依据主张率和评分一致性。
- 对关键指标做成对比较；未通过门槛不得仅凭“感觉更自然”上线。

### 10.5 安全测试

- 项目文件中的 Prompt Injection 不得改变系统权限或泄露其他材料。
- 恶意 README 不得指挥 Agent 忽略规则、调用未授权工具或上传代码。
- 使用含测试密钥、个人信息和版权材料的夹具验证过滤与脱敏。
- 验证被识别的敏感值不会出现在切片、向量索引、模型请求、日志或报告中。
- 验证跨用户、跨项目、跨会话数据隔离。

## 11. 评估方法

评估分为离线质量、在线体验和系统性能三层。

### 11.1 项目快照与面试视图质量

| 指标 | 定义 |
| --- | --- |
| Fact precision | 标记为事实的 Claim 中，确有证据支持的比例 |
| Fact recall | 黄金事实中被系统识别的比例 |
| Citation validity | 引用位置真实存在且支持该 Claim 的比例 |
| Inference calibration | 不同置信度区间与人工认可率的一致程度 |
| Unknown usefulness | 未知项中被专家认为值得面试追问的比例 |
| Module coverage | 黄金关键模块中被识别并正确描述职责的比例 |
| Thread coverage | 黄金端到端链路中被识别且步骤、模块关系基本正确的比例 |
| View relevance | 给定方向与范围后，进入面试视图的证据中确实有用的比例 |

MVP 优先保证 Precision 和 Citation validity，不用虚假的“完整”换取 Recall。

### 11.2 检索质量

- `Recall@K`：黄金相关题是否进入候选集。
- `nDCG@K`：高相关问题是否排在前面。
- 计划适配率：候选问题是否适用于当前追问链阶段和允许动作。
- 重复率：语义相近问题在同一会话重复出现的比例。
- 信息增益：问题是否引出新的项目事实、取舍或缺口。

### 11.3 Supervisor 面试质量

由人工使用 Rubric 盲评：

- 与项目和岗位的相关性。
- 追问是否基于上一轮回答。
- 是否一次聚焦一个主要问题。
- 是否保持难度递进和对话连续。
- 是否始终从合法动作菜单选择，并按照计划推进、分支或结束追问链。
- 必需链阶段是否完成或被明确标记为跳过，而非静默遗漏。
- 是否尊重纠错、拒答和未知边界。
- 是否尊重用户屏蔽的主题，并在范围不明确时正确触发 HITL。
- 是否出现暗示答案、虚构事实或循环追问。

### 11.4 回答评估质量

- 与专家评分的等级一致率和加权 Kappa。
- 反馈中的证据可定位率。
- 同一回答多次评估的稳定性。
- 对不同表达风格的公平性测试。
- “不知道”与胡编回答的区分能力。

评分模型只能辅助形成反馈。MVP 不追求一个看似精确的总分，更重视维度证据和建议质量。

### 11.5 报告价值

用户在复盘后回答：

- 哪些反馈是新的、可信的、可执行的。
- 是否能据此改写答案或补充项目证据。
- 项目改进建议是否符合项目边界，是否减少了用户逐题整理的工作。
- 下一轮是否减少同类遗漏。

关键行为指标包括报告查看率、逐题展开率、建议采纳标记、7 日内复练率和同主题前后表现变化。

### 11.6 系统指标

- 首题等待时间。
- 每轮 P50/P95 响应时间。
- 面试热路径每轮模型调用次数。
- 面试视图和计划生成耗时、缓存命中率。
- 每场计划完成率、非法动作率和 100 轮安全上限触发率。
- 赛后局部证据请求次数。
- 面试恢复成功率。
- 结构化输出失败率。
- 每场模型调用次数与成本。
- 导入成功率和敏感文件过滤率。

## 12. MVP 范围与验收标准

### 12.1 MVP 范围

- 单用户、本地项目目录、中文文本面试。
- 代码与文档导入、敏感信息过滤，生成可审阅并复用的 Project Header、Module、Thread 基础快照。
- 一套人工整理并审核的 AI 软件开发基础题库；题库存题目和元数据，不存标准答案。
- 项目导览、核心链路深挖、横切专项、压力面试、贡献与复盘五种方向，以及全项目、Module、Thread 或专项主题范围。
- 基于方向与范围生成定向面试视图，实例化版本化追问链族并形成结构化计划和动作菜单。
- 面试长度由必需追问链是否完成决定，只展示预计问题数量；100 轮是内部异常循环安全上限。
- 面试规划、题库 RAG Hook、Supervisor、项目版答案、理想版答案和报告等核心角色中，面试热路径只有 Supervisor 调用模型；离线题库整理不阻塞面试或报告。
- 层级主题管理、HITL 范围确认，以及可见、可撤销的会话级主题屏蔽。
- 连续面试上下文、追加式项目事实 Overlay，以及明显冲突的用户确认流程。
- 每道实际问题的收藏和差评入口；改写题与生成题进入待整理队列，不能自动入库。
- 完整历史、逐题反馈、双版本参考答案和项目改进建议。
- 候选题收集、查重结果展示和人工批准，不做自动发布。

### 12.2 MVP 验收标准

在黄金项目包上：

- 事实引用有效率不低于 95%。
- 不允许出现跨项目证据泄露。
- 参考答案、事实核验和评分信息进入 Supervisor 上下文的次数为 0。
- 面试热路径不得触发源文件局部检查；每轮除题库检索外只调用一次 Supervisor 模型。
- 已识别的敏感值进入索引、模型上下文、日志或报告的次数为 0。
- 至少 90% 的会话能在模型单次失败后恢复，而不重复记账或重复提问。
- 人工评审认为“与项目相关”的问题比例不低于 85%。
- 同一会话语义重复题比例低于 10%。
- Supervisor 选择动作菜单外 `plan_action_id` 的次数为 0；必需链未完成或明确跳过前，系统不得自行提议结束。
- 用户屏蔽的主题从下一轮起不再进入动作菜单、检索候选或最终问题；对应必需阶段必须显式记为 `waived_by_user`。
- 项目事实修正不得原地覆盖证据基线；未经赛后核验的用户确认只作为当前会话 Overlay。
- 正常测试会话触发 100 轮安全上限的次数为 0。
- 单次差评和低使用频率不得自动删除或降权题目，任何正式题库变更都需要人工批准。
- 报告中的每个能力判断都能指向至少一段用户回答。
- 报告中的每条项目改进建议都能追溯到项目证据、面试对话或理想版答案。
- 用户可以导出完整会话与报告，并删除项目及其派生数据。

这些数值是首版工程门槛，需在积累真实样本后重新校准。

## 13. 分阶段开发计划

### Phase 0：可行性原型

- 使用 2～3 个固定项目验证 Module/Thread 快照 Schema。
- 建立首批追问链族，以及 100～300 道带主题和适用链阶段元数据的种子题。
- 用命令行跑通“导入—基础快照—方向/范围—面试计划—面试—报告”。
- 验证基础快照与面试视图复用、动作菜单约束、上下文隔离和离线评估框架。

### Phase 1：MVP

- Web 项目管理和基础快照审阅。
- 面试方向、范围、预计问题数量和结构化计划。
- 可暂停恢复的文本面试。
- 追问链进度、动作菜单、主题屏蔽、HITL 范围确认和 Supervisor 结构化输出。
- 项目事实冲突确认、问题收藏与差评。
- 逐题与整场报告。
- 候选题池和人工审核。
- 基础安全、追踪、成本和质量看板。

### Phase 2：训练闭环

- 基于历史薄弱项自动安排复练。
- 同一问题的跨轮回答对比。
- 项目类型模板和用户自定义评估重点。
- 扩充和细化追问链族，并基于真实项目回放调整适用条件与分支。
- 离线题库整理 Agent、候选题维护队列和基于反馈的受控重排实验。

### Phase 3：扩展

- 语音面试与转写。
- GitHub/GitLab、Issue、PR、提交历史接入。
- 教师或带教者工作台。
- 在获得足够质量数据后，探索受控的半自动题库晋级。

## 14. 主要风险与缓解

| 风险 | 后果 | 缓解措施 |
| --- | --- | --- |
| 项目快照幻觉或会话修正跑偏 | 提问建立在错误事实之上 | 证据基线不可变、明显冲突才确认、追加式 Overlay、赛后核验 |
| 面试视图与方向不匹配 | 导览过深或专项证据不足 | 方向/范围定向取证、视图缓存键、黄金项目回归 |
| 追问链过于僵硬 | 面试退化为固定问卷 | 链只定义阶段目标与完成条件，具体问题由 Supervisor 自适应生成 |
| 追问链无法收束 | 对话过长、成本失控 | 合法转移、完成条件、无进展处理和 100 轮异常安全上限 |
| 多 Agent 串扰 | 问题暗示答案，评估失真 | Supervisor 与两类答案 Agent 隔离、单向产物流、泄漏测试 |
| 评分伪精确 | 用户误信一个总分 | 展示证据、区间与置信度，弱化总分 |
| 题库污染 | 迭代后质量持续下降 | 候选池、查重、人工审核、版本回滚 |
| 私有代码泄露 | 严重信任与合规问题 | 最小授权、敏感过滤、数据隔离与删除 |
| 成本与延迟过高 | 面试节奏断裂 | 项目快照复用、热路径单次 Supervisor 调用、赛后答案并行生成 |
| 过度查证 | Supervisor 频繁读取代码导致延迟 | 面试中不做事实核验，局部证据检查只用于赛后分析 |
| 过度追问单点 | 覆盖不足、体验压迫 | 链阶段完成条件、有限动作菜单、无进展处理、HITL 屏蔽与撤销 |
| 用户诱导泄漏答案 | 面试流程被打乱 | 语义识别、结构化动作、系统 Prompt 和多语言回归测试 |
| 用户背参考答案 | 形成模板化表达 | 延迟展示、约束变体、要求结合证据回答 |

## 15. 待决策问题

已确定的产品边界：首版只服务 AI 软件开发岗位，不提供岗位自由选择。

以下问题不阻塞 Phase 0，但应在 MVP 开发前决定：

1. 首版项目接入只读本地目录，还是一开始就做 GitHub 授权？
2. 种子面经题库如何获得合法可用的内容，版权和审核责任如何处理？
3. 首版追问链族和主题树如何划分，是否需要按项目类型配置不同的适用条件？
4. 私有部署、纯本地模型是否属于首版必须支持的隐私要求？
5. 哪些匿名化的产品事件可以用于改善检索和监督规则，哪些必须完全退出采集？

## 16. 建议的首个验证实验

选取三个已知项目：一个文档完善、一个只有代码、一个由用户口述补充背景。邀请项目作者各完成两轮范围和计划规模相当的面试。

第一轮验证：

- 基础快照中的 Module、Thread 和项目事实是否准确，引用是否真的支持结论。
- 问题是否像在问这个项目，而不是替换名词后的通用八股。
- 追问是否会因回答发生变化。
- 报告是否指出了作者自己未意识到的表达或工程缺口。

第二轮只训练第一轮的两个薄弱主题，验证用户能否给出更具体、更有证据且更完整的回答。若看不到可重复的改善，继续增加 Agent 数量没有意义；那只会让会议纪要变厚。
